## 2. 全题统一思路

四问不是四套互不相关的模型。我们当前形成的是一条逐层增加现实不确定性的微网购电—储能调度主线：

```text
Q1 确定性日内调度
  ↓
Q2 日前计划 + 预测误差 + 5倍紧急购电风险
  ↓
Q3 允许 00/06/12/18 多次更新预测并调整计划
  ↓
Q4 在 Q2/Q3 上再加入动态电价和价格信息集
```

全题一直保留以下统一原则：

1. **先统一时间与单位，再建模。** 题目功率为 kW，10 min 决策槽中的能量统一按 `Δt=1/6 h` 转成 kWh。
2. **储能物理层尽量共用。** SOC、容量、功率、效率和跨日连续性在各问中保持同一套接口，避免每问各写一套。
3. **严格区分“决策时已知信息”和“事后实现值”。** 所有 forecast / price / actual 都带 `known_at` 或等价时间语义，禁止未来信息泄漏。
4. **先简单 baseline，再做有针对性的升级。** 模型复杂度本身不构成理由，只有解决明确缺陷并通过同口径比较，才允许替换主线。
5. **预测指标不能替代调度目标。** MAE、RMSE、WAPE 只用于诊断；只要预测结果会进入购电或储能决策，就必须进行 downstream full replay。
6. **先验证，再写结论。** solver 能运行、生成 Excel、单次测试通过，都不能直接变成论文结论。
7. **代码、模型、结果、图表、论文必须能追到同一 Source of Truth。**

## 3. 共用数据与物理口径

### 3.1 时间粒度

一天按 144 个 10 min 槽处理，正式时间映射采用右端点/ordinal 口径。典型映射：

```text
slot 1   -> (00:00, 00:10]
...
slot 144 -> (23:50, 24:00]
```

这一点直接影响附件读入、预测 target、结果模板写回和跨日 `known_at` 判定。

### 3.2 储能

当前正式/继承口径包含：

- 总容量：12000 kWh；
- SOC 允许范围：`[1200,10800] kWh`；
- 充放电功率上限：5000 kW；
- 每 10 min 最大充/放电能量：`5000/6 kWh`；
- 主解释：`eta_c=eta_d=0.9`；
- SOC 递推：

```text
E_t = E_(t-1) + eta_c * C_t - D_t / eta_d
```

Q1 已对 `sqrt(0.9)` 的替代效率解释做过完整敏感性，因此论文不能写“效率语义不影响结果”。

### 3.3 电网交互

当前模型统一不设置售电收益。原因是题面给出了购电机制，但没有给出售电价格或回购结算规则。

因此：

- 外部电网变量表示购电；
- 多余光伏用 curtailment / 弃光表示；
- Q2 的已购但未利用计划电量和 PV 弃光必须分开记账。

## 4. Q1：确定性储能调度

### 4.1 我们最初要解决的问题

Q1 给出一天固定电价、负荷和光伏预测。核心问题是：在满足负荷、储能功率和 SOC 约束的前提下，怎样安排外部购电和储能充放电，使总购电费用最低。

### 4.2 为什么先用 LP

Q1 的核心变量都可以用连续量表示：

- 电网购电；
- 充电量；
- 放电量；
- SOC；
- 弃光量。

能量平衡、SOC 递推、容量和功率限制均为线性，因此先建立连续 LP。我们没有因为“储能问题常见 MILP”或“网上有人使用 MILP”就直接加整数变量。

### 4.3 两阶段目标

正式模型：`TWO_STAGE_CONTINUOUS_LP`。

Stage 1：

```text
min Σ p_t g_t
```

直接寻找最小购电费用。

Stage 2：

在 Stage-1 optimum 加极小 `epsilon_cost` 的容差内，再最小化电池总 throughput：

```text
min Σ (c_t + d_t)
```

这样做是为了在经济目标几乎不改变的情况下，从可能存在的退化最优解中选择较干净的充放电轨迹。

### 4.4 为什么还做 MILP 对照

我们额外建立了仅增加“充/放电互斥二元变量”的 mutex MILP，作为结构 challenger。

比较重点不是证明 MILP 更高级，而是检查：

- LP 和 MILP 的 Stage-1 最小费用是否一致；
- LP 是否出现同时充放电；
- SOC 轨迹是否有实质差异；
- 引入整数变量是否真正带来决策收益。

最终当前 Frozen 结论为：

`LP_SUFFICIENT_MILP_AS_STRUCTURAL_VALIDATION`

即 LP 保持主模型，MILP 只作为结构交叉验证。

### 4.5 Q1 验证链

Q1 不是在第一次求出成本后就冻结，而是依次检查：

```text
官方附件与时间映射
→ LP 实现
→ NO_STORAGE baseline
→ Stage1/Stage2 objective 独立复算
→ 144 槽 balance / SOC replay
→ LP vs MILP
→ epsilon sensitivity
→ efficiency semantics sensitivity
→ result1 writer/readback
→ Blind Red Team
→ Mathematical Review
→ Freeze
```

### 4.6 当前状态

`Q1 = FROZEN`

正式 Freeze Manifest：

`支撑材料/03_中间结果/Q1/CUMCM2026_C_Q1_FINAL_FREEZE_MANIFEST_R0.md`

因此后续 AI 互动记录可以写“AI 辅助了 LP 建模、代码、结构 challenger、验证和审查”，但 Q1 的正式数字必须引用 Frozen Manifest，不应从聊天复述中重新生成。

## 5. Q2：日前承诺、预测误差与高价紧急购电

## 5.1 从 Q1 到 Q2 的关键变化

Q2 的困难不再只是“已知负荷和光伏后怎么调电池”，而是：

- 00:00 要先决定一天的购电计划 `q_DA`；
- 实际负荷和 PV 会偏离预测；
- 缺电时必须以 5 倍价格紧急购电；
- 原计划买多的电仍要付费；
- 储能要在因果信息下参与补救。

因此 Q2 的本质变成：

`forecast → uncertainty representation → day-ahead commitment → causal storage/recourse → realized settlement`

### 5.2 预测层为什么没有直接上复杂 ML

我们先比较周期和历史基线，并坚持时间顺序验证。原因是赛题数据有明显的周周期结构，而且预测只是下游调度的一个输入层。

早期正式 baseline 为：

- Load：LAG7；
- PV：TRAILING7_MEAN。

随后 rolling-origin 研究得到新的开发绑定：

- Load：`L2 / LAG7`；
- PV：`P3 / ETS_HW_DAILY`；
- combo：`L2_P3`。

最新 XXT 数学回包明确：

```text
FORECAST_BINDING_FOR_OPTIMIZATION = L2_P3
FORECAST_SELECTION_FROZEN = FALSE
```

因此 L2_P3 目前只是三模型优化开发和 pilot 的统一输入，并不代表预测层已经 Freeze。正式 full-year / paper claim 前，仍需在同一最终 causal controller 下完成 forecast-to-decision replay。

### 5.3 为什么出现 Q0.80

如果先忽略储能，只看单个时段，计划购买 `q`，普通计划电价为 `p`，缺电后紧急购电价格为 `5p`，则可写：

```text
J(q) = p*q + 5p*E[(D-q)+]
```

在连续内点处求导：

```text
p - 5p*P(D>q) = 0
```

得到：

```text
F_D(q)=0.8
```

因此 Q0.80 来自题目 1 倍计划购电 / 5 倍紧急购电的非对称代价结构。

论文和 AI 记录应称其为：

- 题目特化风险标定；
- problem-specific analytical calibration；
- 由 5 倍紧急购电边际代价导出的临界分位点。

不能把它写成“新提出的一般风险理论”，也不能把单槽解析结果直接等同于含储能全年系统的全局最优证明。

### 5.4 Q2 当前统一结算口径 S1-A

当前 source-resolved accounting 为：

```text
q - w + r + PV + D = L + C + v
```

其中：

- `q`：已锁定的日前购买量；
- `w`：已经买了但实际没有被利用的计划电量；
- `r`：紧急购电；
- `v`：PV 弃光；
- `C,D`：储能充/放电。

约束：

```text
0 <= w <= q
0 <= v <= PV
```

正式 realized cost：

```text
Σ p*q + Σ 5p*r
```

`w` 是“已付费但未利用的计划电”，不是退款，也不能再减掉 `p*w`；`v` 是 PV 弃光，两者不能混用。

### 5.5 当前三模型公平比较

最新 XXT 数学合同把优化层划成三个候选：

#### M1 — Point LP

`M1_POINT_LP`

用 point forecast 做 day-ahead commitment，作为确定性 baseline。

#### M2 — Q80 LP

`M2_Q80_LP`

根据严格因果的 signed net residual history，按 slot 计算 nearest-rank Q0.80 margin，再用与 M1 相同的 day-ahead model 求购电计划。

它承担“5 倍缺电惩罚下的强风险 baseline”。

#### M3 — stochastic challenger

历史标签仍可写：

`M3_SP_LP_CANDIDATE`

但最新数学类必须明确为：

`TWO_STAGE_STOCHASTIC_MILP_FIXED_SAFETY_R1`

原因是 scenario 下 surplus / deficit 模式的符号取决于一阶段 `q_t`，同时又要满足固定储能安全执行方向和“紧急购电不能用于充电”等条件，当前合同中存在真实 disjunction，因此不能把 exact implementation 偷偷写成连续 LP。

### 5.6 为什么要分 Layer A / Layer B

为了避免“更复杂模型只是因为执行规则更自由而赢”，Q2 当前把比较拆成两层：

**Layer A：不确定性建模公平比较**

- M1 / M2 / M3 尽量使用相同的 fixed-storage / safety execution class；
- 重点比较 point、quantile、scenario 三种 day-ahead uncertainty treatment。

**Layer B：可部署的 causal recourse**

- Point 和 Q80 可以进入相同的 `Q2_RH_FIXED_Q_LP_R1` rolling recourse；
- M3 不能把未来 scenario-specific storage path 直接当作真实日内策略；
- 如果 M3 要升级成可部署主模型，需要新的 nonanticipativity / scenario-tree 或 receding-horizon 合同。

### 5.7 Q2 已经积累过的 Core evidence

在进入最新三模型路线之前，Q2 Core Engine 已经跑过四个全年技术组合：

```text
Point + fixed
Point + rolling
Q80 + fixed
Q80 + rolling
```

这些结果证明 common engine、accounting、writer、full-path replay 可以工作，也暴露了策略排序和 delayed-actual 问题。

但这些只是技术候选 evidence，不能把某个数值最低的组合直接写成 final Q2 winner。

### 5.8 当前 M3 两个需要继续数学裁决的问题

2026-09-12 的 FYQ/Astra 实现窗口已经发现两个需要保留的开放问题。它们目前应记录为：

`PENDING_EXECUTION_FINDING / NOT_YET_FORMAL_VERDICT`

#### A. scenario count 与 cutoff

合同要求 scenario residual target 满足：

```text
target_ts < decision_time
```

Feb1 00:00 决策时，Jan31 slot144 的 target 恰好为 Feb1 00:00，因此严格 cutoff 后该槽不能使用。执行窗口据此发现：Jan31 可能无法形成完整 144-slot scenario，导致“23 个完整日”与合同写的“24 个完整 Jan8–31 trajectories”发生冲突。

在 XXT 修订合同之前：

- 不补造第 24 条；
- 不通过 bootstrap 提高有效样本数；
- 不把这一问题写成已解决。

#### B. fixed safety execution 的 policy-class 公平性

公共 fixed-storage 规则倾向于：参考动作只有在物理不可行时做最小 clipping / cancellation。

而当前 M3 合同给 scenario 执行动作：

```text
0 <= C_st <= Cref_t
0 <= D_st <= Dref_t
```

这允许 optimizer 主动选择更小的执行量，即使 reference action 本来仍可执行。这样可能形成比公共 baseline 更宽的 recourse policy class，从而影响公平比较。

当前处理：

- 用最小数值反例验证两套语义是否会产生不同成本 / SOC / emergency；
- 若复现，M3 标记 `BLOCKED_MATH`；
- 由 XXT 修订数学合同；
- FYQ 不自行加约束掩盖冲突。

### 5.9 Q2 当前状态

```text
M1: implementation / verification active
M2: implementation / verification active
M3: revised MILP contract + open math blockers
Q2_FROZEN = FALSE
Q2_MATHEMATICAL_RESULT_PASS = FALSE
```

因此 AI 互动记录应真实表现 Q2 是一个“提出候选 → 解析推导 → Core 实现 → 发现冲突 → 数学回审 → 再实现”的迭代过程，而不是一次 Prompt 就得到最终模型。

## 6. Q3：多时点预测更新与滚动调整

### 6.1 Q3 相比 Q2 新增什么

Q2 在 00:00 决定计划后，计划本身不再调整；Q3 允许在：

```text
00:00 / 06:00 / 12:00 / 18:00
```

收到新的 PV 预测，并调整后续尚未执行的购电计划。

因此 Q3 的关键不是“换一个预测模型”，而是建立多 vintage 的 rolling commitment system。

### 6.2 当前稳定架构

当前 design-stable contract：

- 已执行槽不可改；
- 所有 forecast/action 必须满足 `known_at <= decision_time`；
- 调整参考采用 `PREVIOUS_ACTIVE_COMMITMENT`；
- base 00:00 plan 只计一次；
- 每次增加/减少计划量按 signed delta 记账；
- emergency purchase 单独记 5 倍账；
- result3 输出的是每个 slot 执行前最后生效的 commitment。

当前候选 controller：

`ROLLING_HORIZON_LP_CANDIDATE_R0`

它仍是候选，必须等 XXT 明确 objective、ledger 和 storage timing 后才能正式实现/选择。

### 6.3 为什么选 rolling LP 作为候选

当前理由来自问题结构：

- commitment delta 可以线性分解；
- SOC 与储能平衡线性；
- 每次只优化未来槽；
- 可复用 Q1/Q2 的 validator；
- 比启发式或 RL 更容易解释和审计。

外部论文只用于证明“day-ahead + intraday rolling/MPC”是合理方法族，不直接搬参数和结果。

### 6.4 Q3 必须做的 baseline

至少比较：

```text
00 only
00 + 06
00 + 06 + 12
00 + 06 + 12 + 18
```

这样才能回答题目“是否有必要增加预测时点”，而不是默认次数越多越好。

### 6.5 当前数据证据的解释

06:00 和 12:00 更新相对 00:00 预测，对剩余时域 PV forecast error 有明显改善，因此值得进入 downstream replay。

18:00 虽然相对误差改善比例很高，但晚间绝对 PV 已很小，所以不能仅凭百分比判断它有高经济价值。最终是否保留 18:00，要看正式调度成本、调整成本和 emergency reduction。

### 6.6 Q3 尚需核实的语义

Freeze 前至少需要：

- `PREVIOUS_ACTIVE_COMMITMENT` 与 coherent original-00 reference sensitivity；
- `DELIVERY_SLOT_PRICE` 与 `ISSUE_TIME_PRICE` sensitivity；
- hourly→10min linear causal interpolation 与 endpoint block hold；
- full SOC replay；
- cross-day continuity；
- no future actual leakage；
- result3 writer/readback。

当前状态：

`DESIGN_STABLE_CANDIDATE / FORMAL_RESULT_NOT_RUN`

## 7. Q4：动态电价下的因果决策

### 7.1 Q4 的主要难点

Q4 不只是把固定电价替换成一张动态价格表。真正的建模问题是：

**在某个决策时点，未来动态电价到底是否已经可知？**

题面没有明确授权“提前知道未来 realized Attachment4 price”，因此当前主线严格区分：

- 历史已经实现的价格；
- 决策时可获得的价格预测；
- 未来真实价格；
- oracle diagnostic。

### 7.2 价格信息接口

每个进入决策的价格都要求带：

```text
target_ts
price_value
known_at
vintage_id
source
```

并满足：

```text
known_at <= decision_time
```

### 7.3 当前 baseline

`CAUSAL_PRICE_LAG7_R0`

即对某未来 slot，使用 7 天前同一 canonical slot 的 realized price 作为简单可审计预测。

先保留这个 baseline 的原因是官方数据表现出很强的周周期。只有当 LAG7 在 downstream replay 中暴露具体缺陷，才引入一个更复杂的 time-aware challenger。

### 7.4 Q4-2 与 Q4-3 的继承关系

Q4-2：

```text
Q2 final contract
+ causal dynamic-price information layer
```

Q4-3：

```text
Q3 multi-stage adjustment contract
+ causal dynamic-price information layer
```

因此 Q2/Q3 的数学合同没有稳定之前，Q4 不能自己重新定义储能和 settlement 以绕开上游问题。

### 7.5 Oracle 的作用

`ORACLE_FUTURE_PRICE_DIAGNOSTIC_ONLY`

允许完整未来真实价格只作为：

- value-of-information gap；
- 理想化比较器；
- 定位价格不确定性真正有影响的时段。

Oracle 不能参与 deployable model selection，也不能写成可实施策略。

当前状态：

`PREDESIGN / FORMAL_MODEL_SELECTION_PENDING / FORMAL_RESULT_NOT_RUN`

## 8. 模型选择的统一方法

我们在四问里逐渐固定了一套选择逻辑：

### Step 1：先把题目机制写清

先确定：

- 决策时点；
- 已知信息；
- 决策变量；
- 目标；
- hard constraints；
- 结算规则；
- 正式输出。

### Step 2：做最简单可解释 baseline

例如：

- Q1：continuous LP；
- Q2：Point LP；
- Q3：00-only；
- Q4：price LAG7。

### Step 3：只有存在明确缺陷才升级

例子：

- Q1 用 MILP 检查充放电互斥是否真的需要；
- Q2 用 Q80 处理 5 倍 shortage asymmetry；
- Q2 M3 用 stochastic MILP 检查 scenario uncertainty 是否提供超出 Q80 的真实价值；
- Q3 增加 06/12/18 是为了量化 forecast update 的决策价值；
- Q4 只有 LAG7 downstream 出现 material defect 才上更复杂价格模型。

### Step 4：同口径比较

候选必须保持：

- 同一数据；
- 同一时间口径；
- 同一 physical constraints；
- 同一 accounting；
- 同一 validator；
- 同一因果信息边界。

否则“更低成本”可能只是偷偷获得更多信息或更宽松的动作权限。

### Step 5：full replay 而不是只看 surrogate

如果预测、quantile、scenario、proxy 会改变正式决策，就要重跑：

```text
upstream estimate
→ decision
→ physical replay
→ accounting
→ final metric
```

### Step 6：最后才 Freeze

进入 Freeze 之前至少要满足：

- current-version validation PASS；
- technical PASS；
- mathematical PASS；
- hard constraint zero violation；
- metrics independently recomputed；
- Evidence Gate 通过；
- 没有未处理的 Mathematical Veto。

## 9. 代码与实验验证的统一步骤

正式实现尽量遵循：

```text
Task / Mathematical Contract
→ TDD / tiny anchor
→ implementation
→ synthetic sanity test
→ official-data solve
→ independent validator
→ full path replay
→ accounting recomputation
→ writer/readback
→ hash / provenance / manifest
→ Mathematical Review
→ Evidence Gate
```

### 9.1 tiny anchor 的作用

小规模手算/合成例主要用来检查：

- objective 方向；
- q0.8 是否实现正确；
- surplus/deficit 分支；
- S1-A source split；
- SOC 上下界；
- no selling；
- no emergency charging；
- deterministic degeneration。

它只能证明局部数学和代码关系，没有资格替代正式数据 replay。

### 9.2 independent validator

重要结果不能只由 solver 自己报告。独立 validator 至少复算：

- balance；
- SOC recursion；
- power limits；
- terminal；
- causality / known_at；
- q immutability；
- S1-A；
- objective；
- result workbook readback。

动态 hard constraints 必须逐槽回放，并记录 `max_violation` 和 `argmax_location`。

### 9.3 为什么经常保留 FAIL / HOLD

赛中出现以下情况时，我们没有为了“论文完整”强行修过去：

- Q1 效率语义有 3% 以上成本差异；
- Q2 delayed actual 出现 `S1_A_W_EXCEEDS_Q`；
- Q2 forecast model 的 WAPE 更好但 downstream 尚未验证；
- Q2 M3 continuous LP 被数学审查否决，改为 MILP；
- Q2 M3 scenario count / recourse fairness 又出现新冲突；
- Q3/Q4 在信息和 settlement 没定之前不跑 formal result。

这些 FAIL/HOLD 本身也是 AI 交互记录中重要的真实过程证据。

## 10. 文献在建模中的实际作用

当前文献使用遵循“支持机制，不搬答案”。

主要角色包括：

- risk-aware day-ahead scheduling：支持 Q2 的不确定性/recourse 母体；
- forecast quality → dispatch cost：支持 forecast-to-decision fidelity；
- robust optimization：作为 challenger 背景，不因为论文存在就替换 Q80；
- day-ahead + intraday MPC / rolling：更适合支撑 Q3 多时点更新；
- receding-horizon storage control：支撑 Q3/Q4 的滚动框架。

参数、风险权重、场景数量、结果数字不能从文献直接移植到本题。

## 11. AI 在这个项目里实际承担了什么

为了后续 AI 使用详情真实可追溯，可把 AI 参与分成以下几类。

### 11.1 题意与数据审计

AI 辅助：

- 拆分四问依赖；
- 检查单位和时间粒度；
- 识别 result 时间错位；
- 识别 known_at / leakage 风险；
- 检查附件字段与模板。

人工责任：

- 对照官方题面确认解释；
- 决定最终采用的合同。

### 11.2 模型候选与选择

AI 辅助：

- LP / MILP 对照；
- Point / Q80 / stochastic 候选；
- rolling horizon 架构；
- causal price baseline；
- 文献原型检索。

人工责任：

- 是否派发；
- 是否采纳；
- 是否扩大模型复杂度；
- 是否进入正式主线。

### 11.3 数学审查

XXT/Astra 类工作主要用于：

- objective / hard constraints；
- q0.8 推导；
- S1-A accounting；
- LP/MILP 数学类判断；
- scenario / nonanticipativity；
- exact anchor；
- Mathematical Veto。

这类 AI 输出即使逻辑看起来完整，也仍需要和实际实现、输入、validator 对齐。

### 11.4 代码与执行

Codex / Work / execution agent 主要用于：

- TDD；
- solver 实现；
- runner；
- replay；
- validator；
- writer/readback；
- manifest / SHA；
- clean replay。

执行窗口自报 PASS 不直接作为 Freeze evidence，必须保留 fresh verification 和独立 review。

### 11.5 论文和图表

AI 可以帮助：

- 搭章节结构；
- 整理模型选择逻辑；
- 把技术 Handoff 转成自然中文；
- 设计图表；
- 做论文—技术事实一致性检查。

但未 Frozen 的数字必须保留 placeholder，Paper Lead 不能自行改技术口径。

## 15. AI 交互记录中应避免的失真表达

不要写：

- “AI 直接完成了最终模型”；
- “Astra 证明了全部结果正确”；
- “Codex 测试通过，所以模型正确”；
- “Q80 是本文首创理论”；
- “预测误差最低的模型就是调度最优模型”；
- “M3 是 LP”——当前正式数学类已修订为 MILP；
- “24 个 scenario 已无争议”——当前实现又发现 cutoff 冲突；
- “Q2/Q3/Q4 已完成”——当前只有 Q1 Frozen；
- “人工重写后就等于人工独立完成”。

建议写：

- AI 提供候选、推导、代码或审查；
- 团队对照题面、运行代码、独立复算或通过角色 Review 进行核验；
- 未通过 Gate 的内容保持 PENDING / HOLD / REJECTED；
- 正式采纳内容绑定具体 artifact。

## 17. 更新规则

建议每次发生以下事件时更新：

- 某问 Freeze；
- 模型类发生变化，例如 LP → MILP；
- 预测输入 binding 改变；
- XXT Mathematical Veto / PASS；
- FYQ full replay 改变策略排序；
- 新的 paper claim boundary；
- AI 参与方式发生重要变化。

更新时保留“之前为什么这么做、后来为什么改”的演化过程。对于 AI 交互记录，这种演化比只保留最终答案更有价值。
